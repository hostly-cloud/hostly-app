# HOSTLY_EDITOR_PRODUCT_MANIFESTO

> Manifiesto oficial del Editor V2 de Hostly.

**Estado:** manifiesto maestro de producto
**Ambito:** vision, filosofia y principios permanentes del Editor V2
**Autoridad:** documento cultural y estrategico para producto, UX, diseno y desarrollo futuro
**Relacion:** sintetiza `HOSTLY_EDITOR_EXPERIENCE_GUIDELINES.md`, `HOSTLY_EDITOR_INTERACTION_MODEL.md`, `HOSTLY_EDITOR_HUMANIZATION_ROADMAP.md` y `HOSTLY_EDITOR_TASK_MODEL.md`
**Horizonte:** referencia estable para los proximos diez anos
**Ultima revision:** 2026-07-05

**Relacion con el sistema actual:** este manifiesto describe por que existe el sistema espacial. No sustituye el contrato tecnico Editor V2 -> TPV ni declara funcionalidades futuras como implementadas.

---

## 1. Por Que Existe El Editor V2

El Editor V2 existe porque un restaurante no se entiende solo desde una lista de mesas.

Un restaurante es espacio, movimiento, servicio, ritmo, zonas, accesos, decisiones, memoria y presion operativa. Es una sala que cambia cada noche. Es una terraza que se abre cuando el tiempo acompana. Es una barra que condiciona el servicio. Es una mesa que siempre da problemas. Es un pasillo que no puede bloquearse. Es una zona que el equipo reconoce sin que nadie tenga que explicarla.

Hostly necesita un Editor porque la hosteleria real ocurre en el espacio.

No basta con vender productos.
No basta con tomar comandas.
No basta con tener un TPV.
No basta con mostrar mesas como botones.

Hostly debe ayudar a un negocio a entender como se opera su restaurante.

El Editor V2 existe para convertir un espacio real en una herramienta visual clara, operativa y humana.

Su promesa no es:

**Dibuja un plano.**

Su promesa es:

**Construye tu restaurante para poder operarlo mejor.**

---

## 2. El Problema Que Resuelve

La hosteleria vive con una tension permanente:

El negocio es fisico, pero muchas herramientas lo tratan como si fuera abstracto.

Un restaurante no es solo ventas, productos y tickets. Es donde ocurre cada decision:

- donde se sienta el cliente;
- por donde pasa el camarero;
- donde se recoge comida;
- donde se forma un atasco;
- que mesas se juntan;
- que zona se llena primero;
- que terraza cambia segun el clima;
- que barra absorbe mas trabajo;
- que acceso debe quedar libre;
- que ambiente ayuda a reconocer el local.

Los sistemas tradicionales suelen simplificar demasiado el espacio o lo convierten en una configuracion tecnica. Hostly no debe caer en ninguno de esos dos extremos.

El Editor V2 resuelve un problema profundo:

**hacer que el espacio del restaurante sea comprensible, operable y reconocible sin obligar al usuario a pensar como tecnico.**

---

## 3. Que Producto Queremos Construir

Queremos construir el editor de espacios para hosteleria mas claro, mas humano y mas operativo del mercado.

No el mas complejo.

No el mas decorativo.

No el mas parecido a una herramienta tecnica.

No el que mas objetos tenga.

Queremos construir un producto que un encargado pueda abrir y sentir:

"Esto va de mi restaurante."

"Puedo empezar."

"No necesito aprender una herramienta rara."

"Puedo montar mi sala."

"Puedo colocar mis mesas."

"Puedo organizar mi servicio."

"Puedo reconocer mi terraza."

"Esto me sirve para trabajar."

El Editor V2 debe ser sofisticado por dentro y sencillo por fuera.

Su grandeza no esta en mostrar su poder.

Su grandeza esta en hacer que el poder parezca natural.

---

## 4. Que Nunca Debe Convertirse

El Editor V2 nunca debe convertirse en un CAD.

Hostly no debe pedir mentalidad tecnica, precision arquitectonica o aprendizaje profesional de dibujo.

El Editor V2 nunca debe convertirse en Paint.

Hostly no debe ser un lienzo libre donde cada usuario inventa su propio sistema sin criterio.

El Editor V2 nunca debe convertirse en un videojuego.

Hostly no debe buscar espectaculo visual, realismo gratuito o efectos que compitan con la operacion.

El Editor V2 nunca debe convertirse en una galeria de objetos.

Hostly no mejora por tener mas elementos. Mejora cuando cada elemento ayuda a entender y operar mejor el restaurante.

El Editor V2 nunca debe convertirse en una exposicion de arquitectura interna.

El usuario no debe pensar en sistemas, fases, documentos, capas, entidades o categorias tecnicas.

El Editor V2 nunca debe convertirse en una demo.

Debe funcionar para restaurantes reales, con prisas reales, espacios imperfectos y decisiones de apertura.

---

## 5. Como Debe Pensar Un Encargado

Un encargado no piensa:

"Voy a usar un editor."

Piensa:

"Tengo que montar mi restaurante."

No piensa:

"Voy a elegir una herramienta."

Piensa:

"Aqui van las mesas."

No piensa:

"Voy a editar una capa."

Piensa:

"Esta puerta debe quedar libre."

No piensa:

"Voy a anadir assets."

Piensa:

"Esta terraza tiene jardineras."

No piensa:

"Voy a organizar sistemas."

Piensa:

"El equipo tiene que poder pasar."

Hostly debe respetar esas frases.

El Editor V2 debe organizarse alrededor de intenciones humanas:

- Crear mis espacios.
- Marcar lo que condiciona.
- Colocar mis mesas.
- Organizar mi servicio.
- Hacerlo reconocible.

Estas no son fases.

Son formas reales de pensar.

El usuario debe poder moverse entre ellas como se mueve mentalmente al preparar una sala: vuelve, ajusta, corrige, cambia una mesa, separa una zona, retoca una terraza y revisa si el servicio funciona.

Crear un restaurante no es lineal.

Hostly debe guiar sin encerrar.

---

## 6. El Primer Minuto

El primer minuto no debe demostrar todas las capacidades del Editor.

Debe generar confianza.

Durante el primer minuto, el usuario debe sentir:

"Entiendo donde estoy."

"Esto habla mi idioma."

"Puedo empezar por algo que reconozco."

"No necesito saber como funciona por dentro."

"La mesa, la sala y el servicio estan cerca."

"Puedo cometer un error y corregir."

Durante el primer minuto, el usuario nunca deberia pensar:

"Que fase toca?"

"Que sistema estoy usando?"

"Donde esta la herramienta correcta?"

"Que significa esta categoria?"

"Por que no puedo hacer esto ahora?"

"Tengo que aprender esto antes de dibujar mi restaurante?"

El primer minuto debe terminar con un avance visible.

No con una explicacion.

El primer exito ideal es sencillo:

**un espacio reconocible con mesas claras.**

Cuando el usuario llega ahi, Hostly ya ha empezado a ganar.

---

## 7. Despues De Veinte Minutos

Despues de veinte minutos, el usuario no debe sentir que ha aprendido un editor.

Debe sentir que ha construido una version util de su restaurante.

Debe poder decir:

"Esta es mi sala."

"Esta es mi terraza."

"Aqui esta la barra."

"Aqui entra el cliente."

"Aqui se sienta la gente."

"Aqui trabaja el equipo."

"Estos pasos quedan libres."

"Esta zona se reconoce."

"Puedo abrir con este plano."

Despues de veinte minutos, el Editor debe haber desaparecido lo suficiente para que el usuario hable de su negocio, no del software.

La medida de exito no es cuantas funciones ha usado.

La medida de exito es si puede mirar el plano y decir:

**Si. Este es mi restaurante.**

---

## 8. Principios Innegociables

1. El usuario construye su restaurante, no aprende un editor.
2. La arquitectura interna nunca debe dominar el lenguaje visible.
3. Las mesas siempre son el foco.
4. El servicio es parte central del plano, no un detalle posterior.
5. La operacion prevalece sobre espacio y ambiente.
6. El espacio existe para explicar donde ocurre la operacion.
7. El ambiente existe para reconocer el local, no para decorar.
8. Lo esencial debe estar cerca.
9. La complejidad debe aparecer solo cuando aporta valor.
10. El primer exito debe llegar pronto.
11. La biblioteca debe ser curada, no acumulativa.
12. Cada elemento debe justificar su presencia.
13. El usuario debe poder corregir sin miedo.
14. La experiencia tactil debe sentirse natural, no simplemente posible.
15. La belleza nunca debe dificultar la lectura de mesas.
16. Ningun material debe competir con la operacion.
17. Ningun objeto ambiental debe ganar a la claridad.
18. El producto debe hablar hosteleria, no software.
19. La simplicidad no significa reducir potencia.
20. La sofisticacion debe sentirse como facilidad.

Estos principios no son preferencias.

Son condiciones de identidad.

## 9. Filosofia De Diseno

El diseno del Editor V2 debe estar al servicio de una idea:

**hacer comprensible un restaurante real.**

El diseno debe ser claro antes que expresivo.

Debe ser profesional antes que llamativo.

Debe ser tactil antes que denso.

Debe ser estable antes que sorprendente.

Debe ser humano antes que tecnico.

El Editor no debe intentar impresionar con complejidad. Debe impresionar por la rapidez con la que una persona entiende que puede usarlo.

Cada decision de diseno debe preguntarse:

- Ayuda a reconocer el restaurante?
- Ayuda a colocar mesas?
- Ayuda a entender el servicio?
- Reduce duda?
- Aumenta confianza?
- Hace que Hostly parezca producto comercial?

Si una decision solo hace que el Editor parezca mas sofisticado, pero no lo hace mas claro, no pertenece al nucleo de Hostly.

---

## 10. Filosofia De Interaccion

Hostly debe interactuar por intencion.

El usuario no debe empezar desde herramientas.

Debe empezar desde lo que quiere conseguir:

- crear una sala;
- dibujar una terraza;
- colocar mesas;
- marcar un acceso;
- organizar una barra;
- dejar libre un paso;
- separar un ambiente;
- reconocer su local.

La interaccion ideal se siente asi:

1. El usuario tiene una intencion.
2. Hostly ofrece el camino mas directo.
3. El usuario ve el resultado.
4. Puede ajustar.
5. Puede cambiar de idea.
6. Puede seguir avanzando.

Hostly debe guiar sin encerrar.

Debe sugerir sin imponer.

Debe revelar sin saturar.

Debe permitir empezar imperfecto y mejorar despues.

Un buen Editor no obliga a saberlo todo antes de crear.

Deja crear para poder entender.

---

## 11. Filosofia Visual

Hostly no busca hiperrealismo.

Hostly busca reconocimiento inmediato.

El plano debe sentirse como una planta premium de hosteleria: clara, sobria, reconocible y operativa.

La jerarquia visual oficial es:

1. Operacion.
2. Espacio.
3. Ambiente.

Las mesas, numeros, estados y puntos de servicio deben leerse antes que materiales, vegetacion o decoracion.

El espacio debe sostener la operacion.

El ambiente debe ayudar a orientarse.

Los materiales son interpretaciones graficas, no fotografias.

La vegetacion es identidad, no protagonista.

El agua, la arena, la tarima, el cesped o la piedra deben ayudar a reconocer una zona, no convertir el plano en una ilustracion.

El Editor debe evitar tres errores visuales:

- parecer un plano tecnico frio;
- parecer un dibujo infantil;
- parecer una escena decorativa donde la operacion se pierde.

La belleza en Hostly tiene una obligacion:

**hacer que el restaurante se entienda mejor.**

El sistema espacial actual debe entenderse como una sola experiencia con dos modos:

- **Modo edicion:** Editor V2 y Documento V2 permiten construir el restaurante.
- **Modo operacion:** TPV usa ese contexto visual cuando existe paridad segura y mantiene fallback operativo legacy cuando no existe.

Esto no convierte el TPV en un editor ni convierte el Editor V2 en runtime de comandas, pagos o reservas. Significa que el restaurante que se configura y el restaurante que se opera deben ser reconociblemente el mismo.

---

## 12. Filosofia Operacional

Hostly es software para hosteleria porque entiende que el restaurante no se gestiona desde pantallas aisladas.

Se gestiona desde una operacion viva:

- mesas;
- sala;
- barra;
- cocina;
- servicio;
- reservas;
- pedidos;
- cobros;
- equipo;
- ritmo;
- errores;
- turnos;
- presion.

El Editor V2 debe estar conectado mentalmente a esa realidad.

Cada mesa tiene una funcion.

Cada barra condiciona trabajo.

Cada pasillo importa.

Cada acceso cambia la experiencia.

Cada estacion de camareros puede mejorar o empeorar el servicio.

Cada terraza necesita una lectura distinta.

El Editor no debe limitarse a representar el restaurante.

Debe ayudar a prepararlo.

Un plano de Hostly esta bien cuando ayuda al equipo a trabajar mejor.

---

## 13. Filosofia De Simplicidad

La simplicidad de Hostly no debe ser superficial.

No consiste en quitar valor.

Consiste en quitar friccion.

Un producto simple no es el que tiene pocas capacidades.

Es el que permite usar capacidades complejas sin obligar al usuario a cargar con la complejidad.

Hostly debe esconder lo que no hace falta en cada momento.

Debe acercar lo esencial.

Debe nombrar las cosas como las nombra el usuario.

Debe evitar preguntas prematuras.

Debe reducir dudas.

Debe permitir que la persona avance antes de entender todos los detalles.

La simplicidad no es una estetica.

Es una postura moral de producto:

**respetar el tiempo, la atencion y el contexto real de quien trabaja en hosteleria.**

---

## 14. Filosofia De Crecimiento Futuro

El Editor V2 debe crecer durante anos sin perder su alma.

Ese crecimiento no debe medirse por cantidad de objetos, opciones o capacidades visibles.

Debe medirse por claridad, utilidad y confianza.

Antes de anadir algo, Hostly debe preguntar:

- Responde a una intencion real?
- Ayuda a crear un restaurante mas rapido?
- Hace el plano mas operativo?
- Reduce carga mental?
- Habla el idioma de la hosteleria?
- Mantiene la jerarquia visual?
- Puede crecer sin convertir la experiencia en ruido?

No toda posibilidad tecnica merece convertirse en producto.

No toda idea visual merece llegar al usuario.

No toda automatizacion mejora la experiencia.

No toda expansion fortalece la vision.

Hostly debe crecer como un producto con criterio, no como una coleccion de capacidades.

El futuro del Editor no esta en hacer mas cosas.

Esta en hacer que cada vez mas restaurantes puedan verse, entenderse y operarse mejor.

---

## 15. Decisiones Que Nunca Deben Tomarse Aunque Sean Posibles

Nunca se debe hacer visible una complejidad interna solo porque existe.

Nunca se debe anadir una opcion si solo sirve para demostrar potencia.

Nunca se debe poner la decoracion por delante de las mesas.

Nunca se debe hacer que un usuario entienda una categoria tecnica para resolver una tarea humana.

Nunca se debe convertir el primer minuto en una configuracion.

Nunca se debe tratar la barra como un objeto decorativo.

Nunca se debe tratar la mesa como un icono mas.

Nunca se debe llenar la biblioteca para parecer completa.

Nunca se debe resolver una mala experiencia con explicaciones largas.

Nunca se debe disenar para el equipo interno antes que para el encargado real.

Nunca se debe confundir precision con calidad.

Nunca se debe confundir realismo con profesionalidad.

Nunca se debe confundir simplicidad con falta de ambicion.

Nunca se debe construir algo que obligue al usuario a pensar mas en Hostly que en su restaurante.

---

## 16. Que Significa Ser Software Para Hosteleria

Ser software para hosteleria no significa tener una categoria llamada restaurantes.

No significa tener mesas en pantalla.

No significa adaptar un sistema generico a un sector.

Significa entender el ritmo del servicio.

Significa entender que una decision pequena puede afectar una noche completa.

Significa entender que la sala, la barra, la cocina y la terraza no son modulos separados en la cabeza de quien trabaja.

Significa entender que el usuario necesita rapidez, claridad y confianza.

Significa entender que el producto debe desaparecer en los momentos de presion.

Significa entender que la belleza solo importa si ayuda a trabajar mejor.

Significa entender que un restaurante no es una abstraccion.

Es un lugar lleno de personas, movimientos, errores, rutinas, urgencias y decisiones.

Hostly debe ganarse el derecho a estar en ese lugar siendo claro, fiable y profundamente respetuoso con la operacion real.

---

## 17. Declaracion Final

El Editor V2 de Hostly existe para que un restaurante pueda verse, entenderse y operarse mejor.

No existe para demostrar tecnologia.

No existe para competir con herramientas tecnicas.

No existe para decorar planos.

Existe para que una persona que conoce su negocio pueda construirlo visualmente sin dejar de pensar como hostelero.

El mejor Editor no sera el que mas se explique.

Sera el que una persona abra y entienda.

El que permita colocar mesas sin friccion.

El que haga evidente donde trabaja el equipo.

El que deje claro que una terraza es una terraza.

El que haga que el usuario mire la pantalla y diga:

**Si. Este es mi restaurante.**

Ese es el producto que Hostly debe construir.

Y cada decision futura del Editor V2 debe proteger esa frase.
